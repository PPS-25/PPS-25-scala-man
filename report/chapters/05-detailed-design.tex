\chapter{Detailed Design}

This chapter refines the architecture described in Chapter~4. Rather than enumerating classes, it explains the
\textbf{invariants}, \textbf{responsibilities}, and \textbf{extension points} that shaped the design. The discussion
is organised by layer; diagrams are included only where they clarify a relationship.

The key choice is a \textbf{functional core}: everything in the model is a value, and every operation upon one yields
another value rather than altering what it was given.

\section{Model}

The model holds \textbf{every game rule and nothing else}. It opens no file, draws nothing, and uses no library beyond
Scala's own and a few types from the Java platform.

Two decisions shaped it. \textbf{First}, a level---the whole state of a game at one instant---is a single value from
which the next is computed. Everything in the model must therefore compose into that value, and nothing in it can keep
state of its own.

\textbf{Second}, the behaviour of modes and enemies must be extensible. Each is consequently expressed as an
implementation point: a new mode or enemy behaviour is implemented independently and registered at its relevant
integration points, leaving existing behaviour unchanged.

\subsection{Value objects and semantics}

Every model object is an \textbf{immutable value}, entirely defined by its contents and comparable without relying on
identifiers. This choice applies not only to positions and movements, but to whole game states, so no part of the model
can keep state of its own.

\textbf{Operations live with their values}, rather than with their callers. A direction added to a position returns an
adjacent position. A movement advanced by a duration gives the movement further along, or reports that it has arrived.
The arithmetic of the maze is therefore written in terms of positions and movements rather than rows and columns.

What follows is that a whole game can be compared with ordinary equality, allowing, for example, the persisted parts of
a saved game to be tested by direct comparison with what was written, with no need for a comparison to be written by hand.

The cost is that every update allocates rather than overwrites, creating a stream of short-lived values. This is
accepted: the complete-update cost is covered in the testing chapter and remains well within a frame budget.

\subsection{Constructing valid values}

The design distinguishes \textbf{invalid external data} from an invalid state created by the game itself. The former
is expected and represented explicitly: parsing and validation return an \texttt{Either} whose left side contains
domain errors, while normal absence, such as an unavailable next move, is represented by \texttt{Option}. This keeps
malformed map and save files out of the playing model without using exceptions for ordinary input failures.

By contrast, values whose callers are exclusively program code protect their invariants at construction. A timed
mode requires a positive duration, a survival mode constrains its speed multiplier, an active bonus requires time
left, and a movement refuses a non-positive crossing time. This is the \textbf{smart constructor} principle applied
at the smallest useful scope: once a value exists, its clients may rely on its invariant instead of checking it again.
The leaderboard makes the same choice with a private constructor and a factory that orders and truncates entries.

A patrol route is the same choice made where absence is a legitimate answer: its constructor is private, and the
factory answers with a route only if the maze offers at least two distinct corners, so a maze with no walkable cell
yields no route rather than an empty one.

\subsection{Level state}
A level is the whole \textbf{domain gameplay state} at one instant, gathered into a single value, at the centre of
Figure~\ref{fig:level}. Technical session state, such as the game loop, countdown, last frame, and rendering, is kept
outside it.

What follows is that saving a game is the writing of one value, and that a test can begin from any situation without
playing its way there: a level with the player standing one cell from a bonus is built rather than reached.

Two of the fields in that figure describe nothing of the present. A turn asked for is kept until it becomes possible,
so a direction requested just before a corner is taken at the first opening rather than lost. The cell the player has
just left serves two rules that would otherwise have nothing to go on: a teleport does not carry back whoever has just
arrived through it, and the anticipating enemy reads from it which way the player is going.

Every rule takes a level and returns the level that follows, and is named after the event it accounts for rather than
after the field it touches, since one rule often touches several: dropping the effects that expired also ends the combo
of defeated enemies. None of them knows what precedes it, so the order they run in is settled in one place, described
further on, and a tick is their composition.

\subsection{Collectibles}

What a maze still holds is kept indexed by the position it lies on, so asking what stands where the player has arrived
is a lookup rather than a search. Collecting returns what remains together with what was taken, which is what the two
fields of the result in Figure~\ref{fig:items} record, so that the stages which follow, the score and the effects, need
not look at the maze a second time to learn what to award.

The two kinds are told apart by what they mean rather than by a flag. Only a standard collectible counts among those
remaining, while a bonus is worth points and grants an effect without ever bringing a level closer to its end. What
follows is that a maze holding bonuses alone is complete from the start, which is a consequence of the rules rather
than a case written into the code.

Collecting is idempotent: a position already emptied yields nothing. Since a player occupies a cell only once the
crossing towards it is complete, standing on a cell just emptied cannot gather it twice, and nothing has to remember
what was taken a moment ago.

\subsection{Effects}
An effect in force is kept as the instant it ends rather than as a countdown to be decremented, which is the map of
expirations in Figure~\ref{fig:items}. Asking which effects apply is asking which of those instants are still ahead.

What follows is that no update walks through the effects to subtract from them, that nothing accumulates rounding, and
that an effect behaves the same whether the frames were regular or not. Granting an effect already in force postpones
its end by the full duration rather than adding to what was left, which is what a player expects of a bonus gathered
twice in quick succession.

The collection knows only which effects are in force, and what an effect means is decided by whoever asks: collision
resolution asks whether invulnerability applies, movement asks how much of the passing time the enemies experience
under a slowdown, and neither effect knows the rules of the other.

What the rest of the program is shown is not those instants but how much of each effect remains, and an effect can be
rebuilt from that figure alone. A saved game therefore carries durations rather than moments, and is taken up again
correctly although the clock of the new session begins elsewhere.

\subsection{Entities and their movement}

Both player and enemy are \textbf{moving entities}: they occupy a maze cell, face a direction, and may be crossing
between adjacent cells. The occupied cell is discrete and changes only on arrival. The crossing and its remaining
time are held separately, so the position is always whole and only drawing interpolates the movement.

Speed is expressed as the time taken to cross one cell, rather than as a distance to be covered per update, making an
entity faster than another on the basis of a model choice rather than frame rate.

An entity is \textbf{independent of the maze}. When asked to move, it receives a predicate defining walkable positions
and refuses a step if the predicate is false. The same type therefore serves player and enemies, and tests can use
hand-written predicates rather than a real map.

The event of two entities meeting is not simply them sharing a cell, but also two entities swapping their respective
positions at the same time. Therefore, an entity remembers the cell it most recently left, and thus a meeting is
recognized in three ways: two entities occupy the same cell, two entities crossing into each other's cells, or two
entities standing where each other just was.

    \caption{An enemy is a moving entity together with its kind; the player is a moving entity and nothing more.}

\subsection{Enemy behavior}

Enemy variation is isolated behind \textbf{\texttt{EnemyMovementStrategy}}. A strategy receives an immutable
\texttt{EnemyMovementContext} and returns an optional next position; it neither changes an enemy nor reads the game
state through a global reference. The context contains exactly the information a decision needs: enemy and player
positions, previous player position, validated maze, teleport permission, and any strategy-specific remembered target.

The \textbf{AI stage orchestrates rather than decides}: it selects a strategy from the enemy kind, builds the context
only for idle enemies, records any retained target, and turns a chosen position into an entity movement. Hunter,
Anticipator, and Patroller thus vary independently while sharing one scheduling rule.

Common navigation lives in \texttt{EnemyMovement}: breadth-first search finds shortest paths through walkable cells
and teleport links, and a fixed neighbour order makes equal paths deterministic. An enemy that has just left a
teleport cannot immediately use it again, preventing a bounce between its two ends.

    \label{fig:enemy-behavior}
\end{figure}

\subsection{Game modes}

\texttt{GameMode} is a \textbf{domain policy}, rather than a flag checked throughout the level. Its operations decide the
current outcome, the scoring rule, any mode-specific bonus or potential score, the time visible to the player, and the amount of time enemies
experience during an update. \texttt{Normal}, \texttt{Timed}, and \texttt{Survival} therefore share movement,
collisions, collectibles, and persistence while differing only where their rules differ.

Timed mode adds a positive limit and gives precedence to its expiration over the normal completion rule. Survival
never yields victory and increases the enemy time multiplier at regular intervals, capped so enemies cannot exceed the
player's base speed. This arrangement keeps a future mode local: implementing one policy does not require adding
mode checks to collision, movement, or rendering code.

    \caption{Game modes are policies over the same level data. They determine the outcome, selected scoring rule, visible time, optional award, and enemy time progression without changing the shared gameplay stages.}
    \label{fig:game-modes}
\end{figure}

\subsection{Scoring rules}

Scoring is split across three responsibilities that change for different reasons:

\begin{itemize}
  \item a \textbf{scoring event} records what happened;
  \item a \textbf{scoring rule} determines what that event is worth in a selected mode;
  \item the \textbf{score tracker} records the resulting points and the current defeat combo.
\end{itemize}

What happened is expressed as a \textbf{scoring event}: collecting a standard collectible, gathering a bonus,
defeating an enemy, finishing without losing all lives, finishing with time to spare, surviving a number of waves.
Events carry only the data needed to score them: a number of lives, a duration left, or a count of waves. The model
can therefore report that something happened without knowing what it is worth.

What it is worth is a \textbf{scoring rule}, implemented through the \textbf{strategy pattern}. A rule maps an event
to an amount of points, and three rules exist, one for each game mode. The pattern is used
because the modes do not simply scale the same scoring differently, but they score different events entirely. Under
the standard rule, points come from what is gathered and whom the player defeats; under the timed rule, points come
from the time remaining on victory, and under the survival rule, they come from the waves outlived by
the player. An event that a rule has no interest in is worth nothing, and is not an error, so each rule stays total
over the whole event type, and rules do not need to know which events the others handle.

The rule enforced is a property of the game mode, and reaches the scoring code as a context parameter, so no part of
the model has to carry it from hand to hand, and none of it decides which rule applies.

What has been accumulated is the \textbf{score tracker}: the points and the combo of consecutive enemy defeats.
Defeating an enemy increases the combo, and each combo increase while in the same period of invulnerability is worth
double the points of the previous one. The combo is broken once the invulnerability effect subsides. The run is kept
inside the tracker in order to allow the doubling effect, since the number of defeated enemies is not recoverable
from any single state of the game.

When a game ends, the score together with whatever the mode awards at the finish becomes a \textbf{result}: a score,
the name of the player, and the instant it was reached. That is the value the leaderboard orders and keeps.

\subsection{Leaderboard creation and updates}

A leaderboard holds the results achieved on one maze in one game mode, ordered from best to worst and no more than one
hundred deep. Results from different mazes or modes are never gathered together.

Combining two leaderboards is the only operation that changes one: recording a result means combining the leaderboard
read from storage with a leaderboard holding the single new result. That operation was deliberately designed
to form a \textbf{monoid}, an algebraic structure consisting of a set, an associative binary operation upon it, and an
identity element for that operation. Leaderboards are the set, combining is the operation, and the empty leaderboard
is the identity. Combining is associative, so it cannot matter how results are grouped, and combining with the empty
leaderboard changes nothing.

Associativity is not free here, because combining also truncates to the best hundred. Were two results able to compare
as equal, which of them made it onto the leaderboard would depend on how the results happened to be grouped. So the
ordering is total: results rank by descending score, ties break by the moment a result was achieved, and any tie
remaining breaks by the name of whoever played.

For the construction of a leaderboard, the \textbf{smart constructor} pattern is used: the constructor is private,
and the only way to obtain a leaderboard is a factory that sorts and truncates whatever list of results it is given.
Every leaderboard is therefore already ordered and already within the cap, which is why asking for the best results
takes them from the top with no need to sort again. The invariant is established once, where the value is made, instead
of being checked wherever it is used.

A maze nobody has played has an empty leaderboard rather than no leaderboard at all. The empty value can be displayed,
combined, and queried for its best results, so no absence case is carried through the application. This is an instance
of the \textbf{null object} pattern that, in this case, also coincides with the identity element of the monoid.

\subsection{Ordered update stages}

\textbf{Ordered updates} represent the mutable-looking phrase ``game tick''. \texttt{GameStateUpdatePipeline[S]} is a value holding an
ordered sequence of functions \texttt{S => S}. Its \texttt{tick} method folds the initial state through AI, movement,
collision and teleport resolution, collection, effect expiration, and the next player step. The order is declared in
one place and can be tested separately from every individual rule.

\begin{lstlisting}
def tick(initialState: S): S =
  List(updateAi, updateMovement, resolveCollisions,
       collectItems, applyBonuses, updateState)
    .foldLeft(initialState)((state, stage) => stage(state))
\end{lstlisting}

This is the functional core in its most compact form: a stage has no access to a hidden current level and returns the
level that follows from the one it receives. The shell can choose when to invoke a tick, but the model fixes what that
tick means.

\begin{center}
  \small
  \texttt{AI} $\rightarrow$ \texttt{movement} $\rightarrow$ \texttt{collisions and teleports} $\rightarrow$
  \texttt{collection} $\rightarrow$ \texttt{effects} $\rightarrow$ \texttt{next player step}
\end{center}

For a level, stages are guarded after terminal states, so later stages cannot accidentally revive a defeated game or
collect an item after victory. Input is intentionally recorded between ticks as a requested direction; the final stage
starts that movement only when the player is stationary and the requested cell is walkable. The result is a deterministic
pipeline whose stages can be replaced in tests without introducing a second update mechanism.

\subsection{Game loop and game clock}

A game in progress is governed by two small values: one decides \textbf{whether time passes}; the other records
\textbf{how much time has passed}.

The \textbf{game loop} is a \textbf{finite state machine} over three states: not yet started, running, or paused. What
makes it a machine rather than a flag is that the legal transitions are declared rather than assumed. Every one of
them goes through a single guarded operation, which is told the states it may be performed from: starting is legal
only from not-yet-started, pausing only from running, resuming only from paused. Anything else is refused. The rules
therefore only live in one place and can be read off the three operations, rather than being spread over multiple
conditions where a loop is changed.

An illegal transition raises an error rather than returning a failure, because nobody playing the game can cause one:
it would mean the program itself had asked for something the machine does not allow. Starting, pausing and resuming are
therefore strict, and they are where the machine's rules are stated and where its tests reach them. The graphical
interface does not use them directly: it has an operation of its own that turns a running loop into a paused one,
and a paused loop into a running one. A pause key pressed at the wrong moment thus has no effect, and the refusals
stay reachable only from code.

\begin{figure}
    \centering
    \includegraphics[width=0.6\linewidth]{../docs/uml/GameLoopStateDiagram.pdf}
    \caption{The state machine. There is no way back to \textbf{not started}, no way from it to \textbf{paused},
        and no final state: a loop is discarded rather than ended.}
\end{figure}

The \textbf{game clock} records how long a game has been played for, and nothing else. Time is handed to it one
interval at a time rather than read from the system; elapsed time is therefore part of the state. A saved game resumes
at exactly the recorded instant, while a paused game simply receives no interval to advance.

\subsection{Reading a maze}

Reading a maze is a \textbf{boundary pipeline} with four deliberately distinct representations. \texttt{MapLoader} performs
file I/O and returns a load error on unreadable input. \texttt{MapParser} converts supported ASCII symbols into a
\texttt{RawMap}, reporting syntactic errors such as an empty file, ragged rows, or unsupported characters.
\texttt{MapValidator} then checks gameplay invariants and returns a \texttt{ValidatedMap}, the only map accepted by
the playing model.

\begin{center}
  \small
  \texttt{UTF-8 file} $\rightarrow$ \texttt{MapLoader} $\rightarrow$ \texttt{MapParser} $\rightarrow$
  \texttt{RawMap} $\rightarrow$ \texttt{MapValidator} $\rightarrow$ \texttt{ValidatedMap}
\end{center}

Validation inspects the raw grid once to collect spawns, collectibles, enemies, and teleport endpoints. Structural
errors are accumulated, so a map author can correct all independent problems in one pass. When the structure is sound,
\texttt{MapReachability} performs breadth-first traversal over walkable orthogonal neighbours and bidirectional
teleport links. Keeping this traversal separate from validation gives the validator the policy decision---which cells
must be reachable---while the traversal owns only graph exploration.

\section{View}
The view draws and collects input, and holds no \textbf{domain rule} of its own. It is given a description of what there is to show and
offers back the intentions of whoever is playing, and it is the only part of the program that knows which graphical
library is in use.

Its shape follows from a constraint that is not aesthetic: the machine that runs the tests has no graphical
environment, so a test instantiating a graphical node breaks the build for everyone. The view is therefore split in
two, a line that runs across Figure~\ref{fig:projection}. One half decides what is to be drawn and is made of pure
functions over immutable descriptions; the other draws, is written against the library, and holds no decision. What
follows is that everything worth asserting lies on the first side of that line, and that the second stays thin enough
to be read rather than tested.

\subsection{Drawing from a projection}
What reaches the view is not the level but a projection of it, a flat description of what is to be shown: where whoever
moves has got to, what is left on the ground, the lives, the score, the effects in force and the time. It is a read
model and not a second game state: it cannot advance a clock, move an entity, or see a field the interface has no
reason to know.

Only what is seen enters that description. The time it carries is reduced to whole seconds because whole seconds are
what is displayed; carried in full it would differ at every frame, and the comparison described further on would have
nothing to discard.

The drawing is layered, which is why the board in Figure~\ref{fig:projection} is handed two different descriptions. The
maze does not change for the whole level, so it becomes a grid of sprites once; whoever moves becomes a frame at every
tick, drawn over it. A crossing is drawn by interpolating along the movement rather than by moving the position, so
that a position stays whole in the model and only the picture is continuous.

How wide a cell is drawn is computed from the shape of the maze and the size of the screen, never below what can still
be seen. The exact fractions are a tuning choice rather than a derived one, chosen so that a maze of any proportion
fills the window without a size being written anywhere.

\subsection{Screens and overlays}
What the application is showing is a value of its own, computed from two sources neither of which can answer alone: the
loop knows whether a game is being played and whether it is on hold, the level knows whether it has been won or lost.
Deriving it from both, in one place, keeps the interface from holding a notion of its own of where the player is.

Over the board there may be a veil, carrying a title, what is read under it, and the choices offered. A game in
progress is covered by nothing, and the menu is not a veil but a screen of its own, since nothing is being played
behind it. A button cannot produce a veil of its own: it raises a command, the application answers with the state that
follows, and screen and veil are derived again from it.

The state of the level reaches the veil only if the veil asks for it, and a game in progress never does. The veil
depends on the loop as well as on the level, as Figure~\ref{fig:screens} shows, and therefore cannot be part of the
projection. What follows is that the score of a finished game survives on screen: the veil is computed again only when
the screen changes, so the figures read on it are those of the moment the game ended.

\section{Controller}
The controller sits between the model and the view, translating what the player does into changes of the game and what
the game becomes into something the view can draw. It holds no \textbf{domain rule} and draws nothing, and it is the layer at which the
program as a whole is a value.

\subsection{The application as a value}
The state of the program is one value: whether a menu is showing or a game is being played, the way the outside world
is reached, the tuning the modes are played by, and any transient application notice awaiting processing. Every command produces the next
application rather than modifying the present one. What follows is that a transition can be read as a single
expression, and asserted in a test as an ordinary comparison.

Commands are how the interface offers intentions and never performs them; the controller decides what each one means,
asks the outside world for what it needs, and answers with the application as it then stands. Frame timestamps and
requested directions arrive through their dedicated controller operations. The shell that
owns the window keeps the current application in a mutable reference and replaces it after every event, which is where
a program made of values meets a toolkit that is not.

A request the outside world refuses becomes a sentence rather than an exception, since whoever reads it is playing a
game rather than debugging one. The notice is consumed after the interface processes it, so it cannot repeat itself frame after frame.

The model decides whether a game has ended; the controller detects the first terminal transition. A result is handed
over to be recorded once, however many frames follow, and only if the maze it was played on can be named, since a leaderboard
belongs to a maze and a mode.

\subsection{From frames to game time}

\textbf{The first frame yields no duration}, since there is nothing to measure from. Once the pre-game countdown is complete,
every following frame produces the interval since the one before, and that interval is what the model is advanced by. Therefore, a session
carries the moment of the last frame it saw, which is the only thing in it that has to do with real time.

\textbf{Before entering the model, the interval is bounded}: it is never negative and never longer than fifty milliseconds.
The lower bound guards against a clock that appears to go backwards, while the upper bound guards against a frame
the machine took too long over, like the runtime pausing to collect memory. Without it, the frame following a long
stall would advance the game by everything that elapsed during it, expiring bonuses, jumping the difficulty in survival,
and consuming the timed game limit all between one drawing and the next. The exact number is a tuning choice, not a
derived one, high enough that the ordinary frames can pass untouched, low enough that no stall is felt.

Keys are dealt with in one place only. The arrow keys and W, A, S and D are used for the four directions, escape for
toggling through the paused and running status of the game, and any other key is discarded there rather than being
able to travel onward only to be ignored by the receiver.

A direction is not applied to the player but asked for. The level keeps the request until turning becomes possible,
so if turning is asked just before a corner is taken at the first opening rather than lost.

\subsection{Rendering with change detection}
Between the level and whoever draws it stands the value in Figure~\ref{fig:rendering}: the projection to apply, the
listeners registered against it, and the last description shown. Given a level it computes the description that follows
and passes it on only if it differs from the last. A game session owns it together with the level, and asks it to
notify after every update of the pipeline.

What follows is that a frame in which nothing visible changed does not reach the interface at all, and that how much
detail the projection may carry is settled here rather than in the view: the coarser the description, the more this
comparison can discard.

Notifying answers with an updated rendering rather than changing one in place, so the listeners registered and the last
description shown stay explicit instead of hiding in the state of an observer. It names neither levels nor views, and
the comparison it performs is the ordinary equality the model already provides by being made of values. The same value
serves the tests, which register a listener and therefore observe not only what was drawn but also what deliberately
was not.

Advancing the game and notifying whoever draws are joined in one operation, so that the level which results and the
notice just given about it cannot fall out of step.

\subsection{Adapters design}

\textbf{Adapters are divided by external format}. \texttt{GameFilesEnvironment} owns the user-data
layout and coordinates maps, saves, remembered player names, and leaderboards. The save repository encodes a versioned
properties file containing a copy of the ASCII maze and progress necessary to resume it. Leaderboard storage reads and
writes text rows through small encoder and decoder abstractions, while map loading, parsing, and validation remain a
separate pipeline.

Each adapter translates operational failures into domain-facing errors at its boundary. A missing leaderboard is an
empty value rather than a failure, whereas a malformed save or map returns an actionable explanation. This leaves file
paths, encodings, and I/O exceptions outside both \texttt{Application} policy and the model.

\subsubsection{Storing a leaderboard}

Recorded results reach a file through an interface that mentions neither files nor formats: it can be asked for the
leaderboard, and it can be given one to keep. Everything about how that is done is inside a single implementation,
one file per combination of maze and mode.

A leaderboard is written as one line for each game result, containing the score, the moment it was achieved, and the
name of whoever played, separated by commas. The name is written last to allow players to have commas in their names.

Turning a result into a line and a line back into a result are two separate abilities, because not every line can be
read and converted into a game result, but every game result can be converted into a line.

When storing a game result, the leaderboard that is to receive it is first read from the storage, then combined with
the new game result, and finally saved to the storage once again, as a simple line append to the file would preserve
neither the order nor the cap of the leaderboard.

At the storage boundary, a malformed leaderboard read is a failure naming the first faulty line found. The production
environment presents an unreadable leaderboard requested from the menu as empty, so an optional ranking cannot prevent
the game from being played; recording through that same storage still reports the failure. A missing leaderboard file
is not a failure: no game has yet been recorded on that maze in that mode, so the answer is an empty leaderboard,
which behaves as any other.
